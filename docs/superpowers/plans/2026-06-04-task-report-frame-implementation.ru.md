# План реализации фрейма отчета по задачам

> Это русская версия плана для согласования. Она сохраняет смысл исходного файла `2026-06-04-task-report-frame-implementation.md`, но изложена компактнее и удобнее для чтения. При реализации можно опираться на этот файл как на основной согласованный план, а на английский файл — как на более детализированный рабочий черновик со сниппетами и пошаговыми командами.

## Цель

Собрать и развернуть приложение для VibeCode/Bitrix24, которое открывается как вкладка в карточке элемента смарт-процесса и показывает отчет по задачам, связанным с текущим элементом.

В первой версии приложение должно:

- показывать только задачи, привязанные к текущему элементу смарт-процесса;
- поддерживать фильтры отчета;
- считать итоги по плановым трудозатратам и фактически затраченному времени;
- открывать печатную HTML-версию отчета;
- разворачиваться в VibeCode и подключаться как placement в Bitrix24.

## Архитектура

Приложение делится на две части:

- backend на Node.js + Express;
- frontend на статическом HTML/CSS/JavaScript.

Backend отвечает за:

- получение данных из VibeCode API;
- чтение элемента смарт-процесса и компании;
- поиск связанных задач;
- нормализацию полей задач;
- применение фильтров;
- расчет итогов;
- выдачу JSON для экрана и данных для печатной версии.

Frontend отвечает за:

- чтение контекста Bitrix24 placement;
- fallback на `entityTypeId` и `itemId` из URL при локальной проверке;
- отображение фильтров, таблицы, итогов и состояний загрузки;
- открытие страницы печати с теми же фильтрами.

## Технологии

- Node.js 20
- Express
- dotenv
- встроенный `fetch`
- встроенный `node:test`
- статический frontend без тяжелого фреймворка
- VibeCode API
- placement Bitrix24 `CRM_DYNAMIC_XXX_DETAIL_TAB`

## Принцип порядка работ

Интерфейс нужно поднять раньше, чем было задумано изначально, чтобы уже на раннем этапе можно было открыть страницу и посмотреть результат глазами.

Поэтому план меняется так:

- сразу после каркаса приложения делаем раннюю версию экрана отчета;
- на первом проходе экран может работать на временных данных, stub-ответе или упрощенном endpoint;
- после этого поэтапно подключаем реальные фильтры, нормализацию, API и печатную версию.

## Внешние контракты

Приложение опирается на следующие API и соглашения:

- базовый URL VibeCode API: `https://vibecode.bitrix24.tech/v1`
- авторизация: заголовок `X-Api-Key`
- поиск задач: `POST /v1/tasks/search`
- получение полей задач: `GET /v1/tasks/fields`
- получение элемента смарт-процесса: `GET /v1/items/{entityTypeId}/{id}`
- получение компании: `GET /v1/companies/{id}`
- деплой: `POST /v1/infra/servers/{id}/deploy`
- placement после публикации: `CRM_DYNAMIC_${entityTypeId}_DETAIL_TAB`

## Этапы реализации

### 1. Каркас приложения

Создать базовый Node/Express-проект:

- конфигурация через `.env`;
- `server.js` с health-check;
- базовые npm-скрипты;
- минимальные тесты на чтение конфигурации.

Результат этапа:

- проект запускается локально;
- тесты на конфиг проходят;
- есть чистая база для следующих шагов.

### 2. Ранний просматриваемый frontend

Собрать раннюю версию пользовательского экрана, чтобы можно было быстро увидеть будущий отчет в браузере.

На этом этапе интерфейс должен уже уметь:

- показывать заголовок отчета;
- показывать блок данных по объекту и компании;
- показывать фильтры в визуальном виде;
- показывать таблицу задач;
- показывать блок итогов;
- отображать состояния загрузки, пустого результата и ошибки.

Допускается, что на этом шаге данные будут приходить:

- из временного mock-объекта во frontend;
- или из простого stub-endpoint на backend;
- или из упрощенного JSON без полной бизнес-логики.

Результат этапа:

- страницу уже можно открыть и визуально оценить;
- можно рано согласовать структуру, тексты и компоновку;
- дальнейшая интеграция идет поверх уже видимого интерфейса, а не вслепую.

### 3. Утилиты дат, времени и статусов

Добавить модули, которые:

- хранят список статусов задач и русские подписи;
- разбирают множественный выбор статусов;
- считают диапазоны дат;
- форматируют длительность в `H:MM`;
- суммируют время по набору задач.

Результат этапа:

- все базовые вычисления вынесены в независимые модули;
- есть unit-тесты на статусы, даты и формат времени.

### 4. Нормализация задач, тегов и итогов

Создать слой преобразования ответа API задачи в строку отчета.

На этом этапе нужно:

- привести даты к единообразному виду;
- собрать ссылку на задачу в Bitrix24;
- нормализовать теги;
- подготовить плановые и фактические трудозатраты;
- оставить пустое значение, если поле "Наименование позиции" не найдено.

Результат этапа:

- frontend получает уже удобные для отображения данные;
- логика отображения не зависит от сырого формата API.

### 5. Разбор фильтров и предикаты

Добавить модуль фильтров, который:

- разбирает query-параметры;
- задает период по умолчанию как текущий месяц;
- поддерживает фильтр по тегам;
- поддерживает фильтр по дате завершения;
- поддерживает мультивыбор статусов;
- применяет фильтры к набору задач в памяти.

Результат этапа:

- фильтрация становится прозрачной и тестируемой отдельно от UI и API.

### 6. Клиент VibeCode и поиск поля задачи

Создать HTTP-клиент для VibeCode API и диагностический сценарий.

Нужно:

- вынести все обращения к API в `src/vibecodeClient.js`;
- реализовать безопасную обработку ошибок API;
- через `scripts/discover.js` выяснить технический код поля задачи с именем `Наименование позиции`;
- при необходимости поддержать конфигурацию кода поля через `.env`.

Результат этапа:

- внешние вызовы изолированы в одном месте;
- есть способ проверить структуру живых данных до финальной привязки.

### 7. Сервис отчета

Собрать центральный сервис, который:

1. принимает `entityTypeId`, `itemId` и фильтры;
2. загружает элемент смарт-процесса;
3. определяет компанию;
4. ищет связанные задачи;
5. нормализует задачи;
6. применяет фильтры;
7. считает итоги;
8. возвращает готовую модель отчета.

Сервис также должен корректно обрабатывать:

- отсутствие компании;
- отсутствие задач;
- отсутствие поля `Наименование позиции`;
- неполный контекст элемента.

### 8. HTTP-маршруты Express

Добавить API-маршруты:

- `GET /api/health`
- `GET /api/report`
- `GET /api/report/print-data`

Маршруты должны:

- читать и валидировать параметры;
- вызывать сервис отчета;
- возвращать понятные ошибки;
- не дублировать бизнес-логику;
- заменить временные данные раннего интерфейса на реальные данные сервиса отчета.

### 9. HTML-версия для печати

Сделать отдельную печатную страницу, которая:

- получает те же фильтры, что и основной экран;
- показывает тот же заголовок, таблицу и итоги;
- скрывает интерактивные элементы;
- использует CSS для печати на бумагу или в PDF через системную печать браузера.

### 10. Проверка живого контракта портала

Перед финальным подключением проверить на реальных данных:

- формат привязки задач к элементу смарт-процесса;
- состав полей задачи;
- поведение статусов;
- наличие и код пользовательского поля `Наименование позиции`.

Этот этап нужен, чтобы не строить интеграцию на предположениях.

### 11. Регистрация placement в Bitrix24

После того как приложение работает локально и на тестовом сервере, нужно:

- привязать обработчик как вкладку `CRM_DYNAMIC_XXX_DETAIL_TAB`;
- проверить, что вкладка открывается в карточке нужного смарт-процесса;
- убедиться, что контекст элемента передается автоматически.

### 12. Деплой в VibeCode

Подготовить сценарий публикации:

- сбор файлов приложения;
- упаковка;
- отправка на VibeCode server;
- получение URL опубликованного приложения;
- при необходимости повторная привязка placement к новому URL.

### 13. Сквозная проверка

Перед завершением нужно проверить:

- приложение открывается локально;
- приложение открывается как вкладка в Bitrix24;
- показываются только связанные задачи;
- период по умолчанию — текущий месяц;
- фильтры по тегам, дате завершения и статусам работают;
- можно выбрать несколько статусов сразу;
- итоги считаются правильно;
- ссылка из названия задачи ведет в карточку задачи;
- печатная версия показывает те же данные и подходит для печати.

## Что важно согласовать до старта реализации

Ниже список решений, которые уже заложены в план:

1. Backend и frontend будут максимально простыми, без тяжелого SPA-фреймворка.
2. Источник данных — VibeCode API, а не прямые REST-вызовы из браузера в Bitrix24.
3. Фильтрация частично или полностью выполняется на стороне backend после получения набора связанных задач.
4. Первая версия поддерживает только HTML-печать, без отдельной PDF-генерации.
5. Поле `Наименование позиции` подключается через обнаружение технического кода или через конфиг.
6. Ранний frontend допустимо сначала показывать на mock-данных, если это ускоряет визуальное согласование.

## Риски и открытые вопросы

- Возможны отличия между ожиданиями по статусам в интерфейсе Bitrix24 и фактическими кодами API.
- Placement может потребовать дополнительную настройку уже после первого деплоя.
