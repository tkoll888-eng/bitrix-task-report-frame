# Дизайн: отчет по задачам во вкладке смарт-процесса

> Статус: рабочая спека релиза `1.2`.

## Цель

Создать приложение VibeCode/Bitrix24 в `C:\AI\tasks`.
Приложение добавляет вкладку/frame в карточку элемента смарт-процесса и показывает отчет по задачам, привязанным к текущему элементу.

Первый релиз делаем сфокусированным:

- Показываем только задачи, привязанные к текущему элементу смарт-процесса.
- Добавляем фильтры отчета.
- Показываем итоги по планируемым трудозатратам и затраченному времени.
- Добавляем HTML-версию для печати.
- После реализации деплоим приложение на VibeCode.

PDF, Excel и портал-wide отчеты в первый релиз не входят.

## Размещение

Приложение отображается в карточке элемента смарт-процесса как дополнительная вкладка/frame рядом с данными элемента.

В режиме Bitrix24 frame приложение получает контекст текущего элемента из placement:

- `entityTypeId`
- `itemId`

В локальном режиме контекста Bitrix24 нет. Для локальной проверки пользователь передает элемент вручную через URL:

```text
http://localhost:<port>/?entityTypeId=184&itemId=123
```

Если параметры не указаны, приложение показывает подсказку:

```text
Для локальной проверки добавьте в URL параметры entityTypeId и itemId, например ?entityTypeId=184&itemId=123.
```

## Режимы Авторизации VibeCode

В проекте есть два разных режима доступа, их нельзя смешивать:

- **Deployed Bitrix24 frame / server mode** работает через `VIBECODE_APP_KEY` (`vibe_app_...`) и embedded-сессию пользователя. Когда приложение открыто как вкладка Bitrix24, VibeCode Gateway передает backend-запросам заголовок `X-Vibe-Authorization: Bearer vibe_session_...`. Backend должен отправлять запросы в VibeCode API с `X-Api-Key: <VIBECODE_APP_KEY>` и `Authorization: Bearer <vibe_session...>`.
- **Local/server-to-server diagnostics mode** работает через `VIBECODE_API_KEY` (`vibe_api_...`) без embedded-сессии. Этот режим используется для локальных проверок, discovery-скриптов и прямых диагностических запросов.

Прямой внешний запрос к deployed Black Hole URL, например `/api/report?...`, без открытия приложения внутри Bitrix24 frame не имеет `X-Vibe-Authorization` и может получить `401`. Это ожидаемо и не означает, что frame-режим сломан.

## Основной Экран Frame

Основной встроенный экран должен быть максимально компактным и ориентированным на данные.

На основном экране показываем:

- компактную верхнюю строку с фильтрами;
- компактную строку служебных сообщений (`Загрузка...`, пустой результат, ошибки) под панелью фильтров и перед таблицей;
- кнопку `Печать` в той же верхней зоне;
- таблицу задач как главный визуальный блок;
- компактную итоговую полосу под таблицей.

Frame должен использовать всю доступную высоту области вкладки в карточке смарт-процесса. Приложение должно запрашивать или поддерживать resize embedded-frame через доступный механизм Bitrix24/VibeCode, чтобы отчет занимал видимую область экрана и не оставлял большую пустую нижнюю область под содержимым. Если высота содержимого меняется после загрузки, фильтрации, сортировки или раскрытия элементов интерфейса, высота frame должна актуализироваться.

Так как SDK Bitrix24 подключается асинхронно, resize нельзя считать одноразовым действием. Если при первом вызове `window.BX24.resizeWindow` еще недоступен, приложение повторяет попытку несколько раз после загрузки отчета. Высота передается по полному `scrollHeight` документа с небольшим запасом, чтобы нижняя часть таблицы, пагинация и итоги не скрывались во внутренней рабочей области frame.

Видимая диагностика resize, тестовые строки и экспериментальный вызов `BX24.fitWindow` не должны показываться в рабочей версии. По результатам проверки Bitrix24/VibeCode может ограничивать фактическую высоту области вкладки независимо от запрошенного `resizeWindow`; в этом случае приложение сохраняет best-effort resize и не добавляет пользовательский debug-блок.

Служебные сообщения не должны менять положение панели фильтров. Блок сообщений рендерится ниже фильтров, чтобы при загрузке и смене фильтров верхняя часть экрана не "прыгала".

На основном экране не показываем:

- отдельный заголовок `Отчет по задачам`;
- отдельную плашку `Объект / Компания / Период`.

`Объект`, `Компания` и `Период` показываем только в HTML-версии для печати, а не на основном экране.

## Колонки

Таблица содержит колонки:

- `Дата создания`
- `Статус`
- `Название`
- `Планируемые трудозатраты`
- `Затраченное время`
- `Дата завершения`
- `Крайний срок`
- `Теги`

`Название` задачи обязательно делаем кликабельной ссылкой на задачу в Bitrix24. Целевое поведение по продуктовой логике: открывать стандартную карточку задачи внутри текущего Bitrix24 frame/slider, чтобы пользователь после закрытия оставался в исходной карточке элемента и frame отчета.

Текущее рабочее поведение после проверки платформы: видимый `href` остается обычным рабочим адресом `/company/personal/user/{responsibleId}/tasks/task/view/{taskId}/`, ссылка открывается в новой вкладке через `target="_blank"` и `rel="noopener noreferrer"`. Попытки открыть задачи через `window.BX24.openPath`, URL с `IFRAME=Y&IFRAME_TYPE=SIDE_SLIDER#` и прямой переход внутри iframe не дали стабильного результата для task URL: `openPath` не открывал карточку задачи, а прямой iframe-переход упирался в блокировку `auth2.bitrix24.net`. Поэтому embedded-открытие задачи остается отдельной нерешенной платформенной задачей/багом, а не частью текущего деплоя.

Таблица поддерживает сортировку по клику на заголовки колонок. Первый клик сортирует текущую загруженную выборку по выбранной колонке, повторный клик по той же колонке меняет направление сортировки. Сортировка выполняется на frontend и не меняет активные фильтры или итоги.

Основной экран должен показывать задачи постранично, чтобы frame не загружал на экран длинный список задач сразу. Под таблицей показываем компактную панель пагинации в стиле Bitrix24: текущая страница, кнопки перехода назад/вперед и селектор `На странице` со значениями `20`, `30`, `50`. Значение по умолчанию: `20`.

Пагинация применяется только к отображаемым строкам основного экрана после фильтрации и сортировки. Итоги и `Количество задач` считаются по всей текущей отфильтрованной выборке, а не только по текущей странице. При изменении фильтров, набора тегов, статусов, периода, даты завершения, сортировки или размера страницы интерфейс возвращается на первую страницу. Печатная форма использует весь текущий отфильтрованный отчет и не ограничивается текущей страницей.

## Фильтры

Компактная верхняя строка фильтров содержит:

- `Период`
- `Теги`
- `Дата завершения`
- `Статус`

В первом релизе строка фильтров должна быть постоянно видимой и компактной. Отдельные кнопки `Применить` и `Сбросить` в макете не обязательны, если на этом этапе важнее плотная компоновка.

### Период

`Период` фильтрует по активности задачи.
Задача попадает в отчет, если она была создана или изменена внутри выбранного периода:

```text
Дата создания внутри периода ИЛИ дата изменения внутри периода
```

Значение по умолчанию: `Текущий месяц`.

Фильтр `Период` поддерживает:

- `За все время`
- `Текущий месяц`
- `Прошлый месяц`
- `Текущая неделя`
- `Прошлая неделя`
- `Сегодня`
- `Произвольный период`

Логика диапазонов всегда считается относительно текущей локальной даты пользователя в момент использования:

- `За все время` = без ограничения по дате активности;
- `Текущий месяц` = с первого дня текущего месяца по последний день текущего месяца;
- `Прошлый месяц` = с первого дня предыдущего календарного месяца по последний день предыдущего календарного месяца;
- `Текущая неделя` = с понедельника текущей недели по воскресенье текущей недели;
- `Прошлая неделя` = с понедельника предыдущей календарной недели по воскресенье предыдущей календарной недели;
- `Сегодня` = только текущая дата.

Если выбран `Произвольный период`, в интерфейсе показываем календарный выбор диапазона через нативные поля даты браузера. В визуальном слое это один блок выбора периода, а не отдельная логика быстрых пресетов.

Рядом с фильтром показываем текстовое представление выбранного режима:

- для быстрых календарных пресетов показываем рассчитанный диапазон дат;
- для `За все время` показываем текст `За все время`;
- для `Произвольный период` показываем выбранный интервал или `Выберите даты`, если диапазон еще не заполнен.

### Теги

Фильтр `Теги` работает как комбинированный подбор тегов с логикой `ИЛИ`.

Пользователь может:

- вводить текст без учета технического синтаксиса тегов;
- искать по части названия тега;
- выбирать один или несколько тегов из найденных значений;
- быстро повторно применять ранее использованные наборы тегов.

Правила отбора:

- если выбран один тег, показываем задачи, где есть этот тег;
- если выбрано несколько тегов, показываем задачи, где есть хотя бы один из выбранных тегов;
- поиск идет по буквенным значениям тегов и по части текста, без требования вводить символы-разделители или точный формат Bitrix.

Источник значений для выбора:

- список доступных тегов подгружается автоматически из задач Bitrix24, попавших в текущую выборку данных;
- в подсказках показываем человекочитаемые названия тегов, без технических объектов и служебного синтаксиса.

Поведение интерфейса:

- в поле фильтра остается текстовый поиск для быстрого подбора;
- выбранные теги отображаются отдельными chip-элементами внутри блока фильтра;
- рядом или ниже показываем сохраненные ранее наборы тегов для быстрого повторного выбора;
- также доступен полный список сохраненных наборов.

Сохранение наборов:

- приложение автоматически запоминает уникальные наборы выбранных тегов;
- набор считается уникальным независимо от порядка тегов;
- сохраненные наборы являются общими для всех отчетов в этом браузере, а не только для одного элемента;
- наборы не требуют отдельной кнопки сохранения: они появляются после фактического использования фильтра.

### Статус

У фильтра есть два быстрых пресета:

- `В работе` = `Ждёт выполнения`, `Выполняется`, `Ожидает контроля`, `Отложена`
- `Закрытые` = `Завершена`, `Отклонена`

Пресеты выбирают быстро, но не блокируют ручную поднастройку. После выбора пресета пользователь может добавить или убрать любой отдельный статус вручную из чекбоксов.


Фильтр `Статус` работает как мультивыбор. Пользователь может выбрать один или несколько статусов одновременно, как в интерфейсе Bitrix24.

Фильтр показывает актуальные статусы задач Bitrix24:

- `Ждёт выполнения`
- `Выполняется`
- `Ожидает контроля`
- `Завершена`
- `Отложена`
- `Отклонена`

Внутри приложения статусы мапятся на технические значения для API. Если выбрано несколько статусов, отчет показывает задачи, подходящие под любой из выбранных статусов.

Визуально фильтр `Статус` оформляется как выпадающий список с чекбоксами, а не как одиночный select. Пользователь может одновременно отметить, например, `Ждёт выполнения` и `Выполняется`.

Если не выбран ни один статус, отчет трактует это как `Все статусы`.

## Итоги

Под основной таблицей показываем компактную итоговую полосу.

Итоги считаются по текущей отфильтрованной выборке:

- сумма `Планируемые трудозатраты`;
- сумма `Затраченное время`.

Время показываем в формате `H:MM`.

## Печатная Форма

В верхней панели основного отчета есть две кнопки: `Обновить` и `Печать`.

`Обновить` заново загружает текущий отчет на основном экране с теми же параметрами и текущим контекстом. Она не меняет фильтры и не открывает новую страницу.

Кнопка `Печать` печатает отчет из текущего авторизованного frame через `window.print()`, с текущими примененными фильтрами и уже загруженными данными. Она не должна открывать `/print.html` в новой вкладке: новая вкладка на Black Hole/VibeCode-домене не наследует embedded-сессию VibeCode Gateway и может получить `401`.

Печатная разметка внутри текущего frame содержит:

- автоматически сгенерированное название отчета по компании;
- название объекта;
- название компании;
- строку `Период`, которая в печатной форме показывает значение текущего фильтра `Дата завершения`, не меняя смысл самого фильтра;
- таблицу задач;
- итоги по планируемым трудозатратам и затраченному времени.

Полный контекст отчета в виде `Объект / Компания / Период` обязателен именно в печатной форме.

Для печати используем отдельные CSS-стили:

- скрываем кнопки и интерактивные фильтры;
- скрываем колонку `Теги` в обоих вариантах печати: внутри текущего frame и в legacy `print.html`;
- делаем таблицу читаемой на бумаге;
- перераспределяем ширины печатных колонок в пользу `Название`, чтобы оно получило максимум полезной ширины без ухудшения читаемости статуса, дат и числовых колонок;
- сохраняем шапку печатной формы и блок итогов.

В первом релизе используется только HTML-печать через системную печать браузера. PDF не входит в объем первого релиза.

## Поток Данных

1. Frame открывается внутри карточки элемента смарт-процесса.
2. VibeCode Gateway прокидывает embedded-сессию в backend-запросы как `X-Vibe-Authorization: Bearer vibe_session_...`.
3. Frontend читает placement context.
4. Если placement context недоступен, frontend читает `entityTypeId` и `itemId` из URL для локальной разработки.
5. Frontend отправляет контекст и фильтры на backend.
6. Backend загружает элемент смарт-процесса, чтобы получить название объекта и компанию.
7. В frame-режиме backend ходит в VibeCode API через `VIBECODE_APP_KEY` плюс forwarded `Authorization: Bearer <vibe_session...>`.
8. В локальном диагностическом режиме backend/скрипты могут ходить в VibeCode API через `VIBECODE_API_KEY` без embedded-сессии.
9. Backend загружает задачи, привязанные к текущему элементу смарт-процесса.
10. Backend применяет фильтры, нормализует поля, мапит статусы и считает итоги.
11. Frontend показывает таблицу и итоги.
12. Печатная форма строится из уже загруженной модели отчета в текущем frame и вызывает системную печать браузера.

## Ошибки

Если задач нет, показываем:

```text
По выбранным фильтрам задач не найдено.
```

Если в режиме Bitrix24 frame не удалось определить текущий элемент смарт-процесса, показываем:

```text
Не удалось определить текущий элемент смарт-процесса.
```

Если в локальном режиме не удалось определить элемент, показываем подсказку из раздела `Размещение`.

Если компания не указана в элементе смарт-процесса, отчет все равно строится. В основном экране это не показывается отдельным блоком, а в печатной форме можно вывести, что компания не указана.

### Диагностика Ошибок VibeCode

При ошибках VibeCode приложение должно показывать не только HTTP-статус, но и человекочитаемые детали из ответа API: `message`, `userMessage`, `error.message`, `error.hint` и `error.details`, если они есть.

Для диагностики используем такие правила:

- `401` в локальном режиме означает проблему с `VIBECODE_API_KEY` или выбором ключа. Локальный режим без `X-Vibe-Authorization` должен использовать `VIBECODE_API_KEY`, даже если в `.env` также указан `VIBECODE_APP_KEY`.
- `401` при прямом внешнем запросе к deployed `/api/report` без Bitrix24 frame-сессии ожидаем и не считаем поломкой frame-режима.
- `404` от VibeCode при `GET /items/{entityTypeId}/{itemId}` обычно означает, что передан несуществующий или неверный `itemId` для указанного `entityTypeId`.
- `422` от VibeCode означает, что API отклонил параметры или тело запроса. В этом случае нельзя гадать по одному статусу: нужно вывести детали ответа VibeCode и проверить endpoint, поля фильтра и формат тела запроса.
- Если локальная ссылка использует тестовый `itemId=123`, такой элемент может не существовать. Для проверки нужен реальный ID элемента смарт-процесса.

## Current VibeCode Embedded Auth Correction

- Embedded Bitrix24 mode uses `VIBECODE_APP_KEY` (`vibe_app_...`), not `BITRIX24_WEBHOOK_URL`.
- Local/server discovery can still use `VIBECODE_API_KEY` (`vibe_api_...`).
- VibeCode Gateway passes the user session to the backend as `X-Vibe-Authorization: Bearer vibe_session_...`.
- The backend forwards that value to VibeCode API as `Authorization: Bearer ...` together with `X-Api-Key: <VIBECODE_APP_KEY>`.
- Direct deployed `/api/report` checks outside Bitrix24 frame do not have the embedded session and may return `401`; use the local `vibe_api` path for server-to-server diagnostics.
- Placement publication is done through VibeCode app publishing: `POST /v1/apps/:id/publish` with `CRM_DYNAMIC_<entityTypeId>_DETAIL_TAB` in `placements`.
- Direct Bitrix24 `placement.bind` through incoming webhook is not the active project path.
