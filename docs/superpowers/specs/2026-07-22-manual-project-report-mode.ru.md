# Дизайн: ручной выбор проекта для отчета по задачам

> Статус: проект спецификации для новой волны изменений после релиза `1.3`.

## Причина

Приложение теперь может открываться не только как вкладка внутри карточки смарт-процесса, но и отдельным iframe из списка приложений. В отдельном iframe нет контекста текущего элемента смарт-процесса, поэтому приложение не знает `itemId`.

Раньше для локальной проверки и отдельных запусков приходилось вручную подставлять номер проекта в код или URL. Это нужно заменить штатным ручным режимом.

## Цель

Сохранить текущее поведение внутри карточки смарт-процесса без изменений и добавить режим ручного ввода проекта, когда контекст карточки недоступен.

Тип смарт-процесса фиксирован внутри кода: `entityTypeId = 184`. Пользователь нигде не видит и не редактирует `entityTypeId`; вручную вводится только ID элемента смарт-процесса, то есть `itemId`.

## Режимы Работы

### Контекстный Режим

Если приложение получает `entityTypeId` и `itemId` из Bitrix24 placement или из URL-параметров, оно работает как сейчас:

- сразу загружает отчет;
- строит задачи по текущему элементу смарт-процесса;
- не показывает дополнительное поле ручного выбора проекта;
- сохраняет текущие фильтры, сортировку, пагинацию и печать.

### Ручной Режим

Если `itemId` не найден:

- приложение не загружает отчет автоматически;
- приложение не показывает демо-строки вместо реального отчета;
- в панели фильтров появляется дополнительное поле `ID проекта`;
- по умолчанию поле пустое;
- таблица и итоги остаются пустыми;
- пользователь видит сообщение: `Введите ID проекта, чтобы загрузить отчет по задачам.`

После ввода ID проекта приложение строит отчет с параметрами:

```text
entityTypeId=184
itemId=<введенный ID проекта>
```

Остальные фильтры работают так же, как в контекстном режиме: период, теги, дата завершения, статус, сортировка, пагинация и печать.

`entityTypeId=184` используется только внутренне при формировании запроса. Во фронте не должно быть поля, подписи или настройки для выбора типа смарт-процесса.

## UI

Поле `ID проекта` показывается только в ручном режиме, когда приложение не получило `itemId` из placement или URL.

Поле размещается в верхней панели фильтров рядом с существующими фильтрами. Оно должно быть компактным и не ломать текущую раскладку iframe.

Ожидаемое поведение:

- пустое значение не запускает загрузку;
- ввод числового ID и применение фильтра запускают загрузку отчета;
- при смене ID проекта страница пагинации сбрасывается на первую;
- кнопка `Обновить` перезагружает отчет только если ID проекта указан;
- кнопка `Печать` доступна только после загрузки отчета, как и сейчас.

## Backend

Маршрут `/api/report` остается основным контрактом и по-прежнему требует `entityTypeId` и `itemId`.

Ручной режим реализуется на frontend: если контекст отсутствует, frontend подставляет фиксированный `entityTypeId=184` и отправляет введенный пользователем `itemId`.

Новый endpoint не нужен.

## Конфигурация

Фиксированный `entityTypeId=184` нужно вынести в явную внутреннюю константу для ручного режима.

Предпочтительный вариант: использовать frontend-константу с понятным именем, например `MANUAL_MODE_ENTITY_TYPE_ID = '184'`, и покрыть ее тестами через сериализацию query.

Если позже тип смарт-процесса нужно будет изменить, его меняем внутри кода отдельной правкой. Публичный выбор `entityTypeId` в эту волну не добавляем.

## Ошибки и Пустые Состояния

Если контекста нет и ID проекта пустой, это не ошибка API. Показываем спокойное информационное сообщение и пустой отчет.

Если ID проекта введен, но VibeCode возвращает ошибку, показываем текущую диагностику ошибки без изменения поведения.

Если ID проекта введен, но задач нет, показываем текущее сообщение пустого результата: `По выбранным фильтрам задачи не найдены.`

## Локальная Проверка

Перед деплоем обязательно проверить локальный режим без параметров `entityTypeId` и `itemId` в URL:

```text
http://localhost:<port>/
```

Ожидается:

- приложение открывается без демо-строк;
- отображается поле `ID проекта`;
- до ввода ID проекта API-запрос к `/api/report` не выполняется;
- после ввода реального ID проекта отчет загружается с `entityTypeId=184`;
- фильтры, сортировка, пагинация, обновление и печать работают для загруженного отчета.

Также нужно проверить прежний локальный контекстный режим:

```text
http://localhost:<port>/?entityTypeId=184&itemId=<id>
```

Ожидается:

- поле `ID проекта` не показывается;
- отчет загружается сразу;
- поведение совпадает с текущим релизом.

## Тестирование

Нужно обновить или добавить тесты для следующих случаев:

- чтение контекста из placement остается без изменений;
- чтение контекста из URL остается без изменений;
- отсутствие `itemId` переводит frontend в ручной режим;
- query для ручного режима строится с `entityTypeId=184` и введенным `itemId`;
- без введенного `itemId` frontend не должен вызывать `/api/report`;
- основной HTML содержит элементы ручного режима;
- preview/demo-строки больше не используются как fallback для отсутствующего контекста;
- `/api/report` продолжает валидировать обязательные `entityTypeId` и `itemId`.

## Вне Области

В эту волну не входит:

- поиск проекта по названию;
- выбор другого `entityTypeId`;
- загрузка всех задач без выбранного проекта;
- новый backend endpoint;
- изменение логики связи задач с элементом смарт-процесса;
- изменение деплойного механизма VibeCode.
